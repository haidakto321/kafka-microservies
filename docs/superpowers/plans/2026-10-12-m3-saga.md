# M3 - Full saga: Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Finish the orchestrated order saga - payment-service, compensation (`ReleaseStock`), order events with a notification-service fan-out - so an order ends `CONFIRMED`, `CANCELLED / OUT_OF_STOCK` or `CANCELLED / PAYMENT_FAILED` with the stock put back, checked end to end and written up for a Kafka beginner.

**Architecture:** order-service stays the conductor: each reply moves the order one state and writes the next message to its outbox in the same transaction (`ChargePayment` to payment-commands, `ReleaseStock` to inventory-commands, `OrderConfirmed` / `OrderCancelled` to order-events). payment-service is a new service built like inventory (outbox, processed-message table, error handler, own database `payment_db`). inventory-service learns `ReleaseStock` (natural idempotency: only a `RESERVED` reservation is released). notification-service is a new, database-less consumer of order-events in its own consumer group - deliberately not idempotent.

**Tech Stack:** Java 21, Spring Boot 3.5.6, Spring Kafka 3.3, Spring Data JPA, Flyway, PostgreSQL 17.4, `apache/kafka-native:4.3.1`, Testcontainers.

## Decisions this plan makes (not spelled out in the spec)

1. **Compensation is fire-and-forget, as in the spec's topic table** (no `StockReleased` reply). On `PaymentFailed`, order-service cancels the order and writes `ReleaseStock` + `OrderCancelled` in one transaction. The outbox and the error handler make sure `ReleaseStock` arrives; inventory's natural idempotency makes a repeat harmless. Cost: the order says `CANCELLED` a moment before the stock is back (the end-to-end check waits for it).
2. **Every service declares a `NewTopic` for every topic its outbox writes to** (order-service: payment-commands and order-events too). With auto-create off, one row for a missing topic would block the whole outbox (M2 review note).
3. **payment-service copies the M2 classes** (outbox, processed message, error handler, scheduling) - same "database per service" decision as M2. No lock-conflict retry: there is no shared row to fight over.
4. **The payment rule lives in `Payment.charge(...)`**: `amount <= 1000.00` succeeds, anything more fails with reason `AMOUNT_OVER_LIMIT` (spec: "fails on purpose when the total is over 1,000"). One payment per order, insert-only (natural idempotency).
5. **A `ChargePayment` without an amount is invalid data**: `InvalidMessageException`, straight to the DLT (spec 6.4).
6. **notification-service has no database and is not idempotent** (spec 6.2). It still gets the shared error handler and `order-events.DLT`, so a broken event cannot block it.
7. **`OrderSagaService` keeps one method per reply type** (`onStockReserved`, `onStockReservationFailed`, `onPaymentSucceeded`, `onPaymentFailed`), each joining the handler's transaction.
8. **`scripts/e2e-check.ps1`** is the spec's end-to-end check: three orders (Keyboard, Laptop, mug), wait for the final state, check the Laptop stock came back.

## Review Focus

1. **`ReleaseStock` delivered twice, or for an order that never reserved** - stock comes back exactly once; nothing happens without a `RESERVED` reservation. Pinned by `aSecondReleaseChangesNothing`, `releasingWithoutAReservationChangesNothing` (Task 2).
2. **A late reply after the saga moved on** - `PaymentSucceeded` for a cancelled order and `PaymentFailed` for a confirmed order change nothing and send nothing. Pinned by `aLatePaymentSucceededDoesNotConfirmACancelledOrder`, `aPaymentFailedAfterConfirmationChangesNothing` (Task 1).
3. **A duplicate `StockReserved`** - the customer is charged once (one `ChargePayment` row). Pinned by `aDuplicateStockReservedChargesOnlyOnce` (Task 1); a duplicate `ChargePayment` makes one payment: `aDuplicateChargeIsProcessedOnce` (Task 3).
4. **The payment limit boundary** - exactly 1,000.00 succeeds, 1,000.01 fails. Pinned by `exactlyTheLimitSucceeds`, `overTheLimitFailsWithAReason` (Task 3).
5. **A `ChargePayment` with no amount** - goes to `payment-commands.DLT` without retries, no payment row. Pinned by `aChargeWithoutAnAmountGoesToTheDeadLetterTopic` (Task 3).

`OrderSagaService.java` (whole file):

```java
package com.kafkademo.order.order;

import com.kafkademo.contracts.MessageTypes;
import com.kafkademo.contracts.Topics;
import com.kafkademo.contracts.payload.ChargePayment;
import com.kafkademo.contracts.payload.OrderCancelled;
import com.kafkademo.contracts.payload.OrderConfirmed;
import com.kafkademo.contracts.payload.ReleaseStock;
import com.kafkademo.order.outbox.OutboxWriter;
import java.time.Clock;
import java.util.Optional;
import java.util.UUID;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

/**
 * The saga "conductor" (orchestration): reacts to each reply and decides the next step.
 * The state change and the message it causes are saved in the same transaction (outbox):
 * <pre>
 *   StockReserved          -> STOCK_RESERVED, send ChargePayment
 *   StockReservationFailed -> CANCELLED (OUT_OF_STOCK), announce OrderCancelled
 *   PaymentSucceeded       -> CONFIRMED, announce OrderConfirmed
 *   PaymentFailed          -> CANCELLED (PAYMENT_FAILED), send ReleaseStock (compensation), announce OrderCancelled
 * </pre>
 * A reply that does not fit the order's state (late or duplicate) is logged and ignored, and sends nothing.
 */
@Service
public class OrderSagaService {

    private static final Logger log = LoggerFactory.getLogger(OrderSagaService.class);

    private final OrderRepository orders;
    private final OutboxWriter outbox;
    private final Clock clock;

    public OrderSagaService(OrderRepository orders, OutboxWriter outbox, Clock clock) {
        this.orders = orders;
        this.outbox = outbox;
        this.clock = clock;
    }

    @Transactional
    public void onStockReserved(UUID orderId) {
        Optional<Order> found = find(orderId, MessageTypes.STOCK_RESERVED);
        if (found.isEmpty()) {
            return;
        }
        Order order = found.get();
        if (!order.markStockReserved(clock.instant())) {
            ignored(order, MessageTypes.STOCK_RESERVED);
            return;
        }
        outbox.add(Topics.PAYMENT_COMMANDS, orderId, MessageTypes.CHARGE_PAYMENT, new ChargePayment(order.getTotal()));
        log.info("Order {} -> STOCK_RESERVED, ChargePayment {} sent", orderId, order.getTotal());
    }

    @Transactional
    public void onStockReservationFailed(UUID orderId) {
        Optional<Order> found = find(orderId, MessageTypes.STOCK_RESERVATION_FAILED);
        if (found.isEmpty()) {
            return;
        }
        Order order = found.get();
        if (!order.markStockReservationFailed(clock.instant())) {
            ignored(order, MessageTypes.STOCK_RESERVATION_FAILED);
            return;
        }
        outbox.add(Topics.ORDER_EVENTS, orderId, MessageTypes.ORDER_CANCELLED,
                new OrderCancelled(CancelReason.OUT_OF_STOCK.name()));
        log.info("Order {} -> CANCELLED (OUT_OF_STOCK)", orderId);
    }

    @Transactional
    public void onPaymentSucceeded(UUID orderId) {
        Optional<Order> found = find(orderId, MessageTypes.PAYMENT_SUCCEEDED);
        if (found.isEmpty()) {
            return;
        }
        Order order = found.get();
        if (!order.confirm(clock.instant())) {
            ignored(order, MessageTypes.PAYMENT_SUCCEEDED);
            return;
        }
        outbox.add(Topics.ORDER_EVENTS, orderId, MessageTypes.ORDER_CONFIRMED,
                new OrderConfirmed(order.getProductId(), order.getQuantity(), order.getTotal()));
        log.info("Order {} -> CONFIRMED", orderId);
    }

    @Transactional
    public void onPaymentFailed(UUID orderId) {
        Optional<Order> found = find(orderId, MessageTypes.PAYMENT_FAILED);
        if (found.isEmpty()) {
            return;
        }
        Order order = found.get();
        if (!order.markPaymentFailed(clock.instant())) {
            ignored(order, MessageTypes.PAYMENT_FAILED);
            return;
        }
        // Compensation: the stock was already taken, so ask inventory to put it back.
        // A saga cannot roll back another service's commit - it sends a new command that undoes it.
        outbox.add(Topics.INVENTORY_COMMANDS, orderId, MessageTypes.RELEASE_STOCK,
                new ReleaseStock(CancelReason.PAYMENT_FAILED.name()));
        outbox.add(Topics.ORDER_EVENTS, orderId, MessageTypes.ORDER_CANCELLED,
                new OrderCancelled(CancelReason.PAYMENT_FAILED.name()));
        log.info("Order {} -> CANCELLED (PAYMENT_FAILED), ReleaseStock sent", orderId);
    }

    private Optional<Order> find(UUID orderId, String replyType) {
        Optional<Order> found = orders.findById(orderId);
        if (found.isEmpty()) {
            log.warn("{} for unknown order {} - ignored", replyType, orderId);
        }
        return found;
    }

    private static void ignored(Order order, String replyType) {
        log.warn("{} ignored: order {} is already {}", replyType, order.getId(), order.getStatus());
    }
}
```

```java
    private final EnvelopeCodec codec;
    private final Clock clock;

    public PaymentCommandHandler(ProcessedMessageRepository processedMessages, PaymentRepository payments,
                                 OutboxWriter outbox, EnvelopeCodec codec, Clock clock) {
        this.processedMessages = processedMessages;
        this.payments = payments;
        this.outbox = outbox;
        this.codec = codec;
        this.clock = clock;
    }

    /**
     * Handles one command in ONE transaction: the duplicate check, the payment and the reply (an outbox row)
     * are committed together, or not at all.
     */
    @Transactional
    public void handle(MessageEnvelope envelope) {
        if (processedMessages.existsById(envelope.messageId())) {
            log.info("Duplicate message {} ({}) for order {} - already processed, skipped",
                    envelope.messageId(), envelope.type(), envelope.orderId());
            return;
        }
        processedMessages.save(new ProcessedMessage(envelope.messageId(), clock.instant()));
        switch (envelope.type()) {
            case MessageTypes.CHARGE_PAYMENT -> charge(envelope);
            default -> log.warn("Ignoring unknown command type '{}' (messageId={})", envelope.type(), envelope.messageId());
        }
    }

    private void charge(MessageEnvelope envelope) {
        ChargePayment command = codec.payload(envelope, ChargePayment.class);
        if (command.amount() == null) {
            // Invalid data can never succeed: not retryable, straight to the DLT (spec 6.4).
            throw new InvalidMessageException("ChargePayment " + envelope.messageId() + " has no amount");
        }
        Payment payment = payments.save(Payment.charge(envelope.orderId(), command.amount(), clock.instant()));
        if (payment.succeeded()) {
            outbox.add(Topics.SAGA_REPLIES, envelope.orderId(), MessageTypes.PAYMENT_SUCCEEDED,
                    new PaymentSucceeded(command.amount()));
        } else {
            outbox.add(Topics.SAGA_REPLIES, envelope.orderId(), MessageTypes.PAYMENT_FAILED,
                    new PaymentFailed(command.amount(), payment.getReason()));
        }
        log.info("Order {}: payment of {} {}", envelope.orderId(), command.amount(), payment.getStatus());
    }
}
```

```java
import com.kafkademo.contracts.EnvelopeCodec;
import com.kafkademo.contracts.MessageEnvelope;
```
```java
import com.kafkademo.contracts.MessageTypes;
import com.kafkademo.contracts.Topics;
```

```java
import com.kafkademo.contracts.payload.OrderConfirmed;
import org.apache.kafka.clients.consumer.ConsumerRecord;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.kafka.annotation.KafkaListener;
import org.springframework.stereotype.Component;

/**
 * Fan-out: this service reads order-events in its own consumer group, so it gets every event, whoever else reads
 * the topic. NOT idempotent on purpose (spec 6.2): a duplicate event means a duplicate log line - harmless.
 * A real service would send an e-mail; then a duplicate would matter, and it would need a processed-message table.
 */
@Component
public class OrderEventListener {

    private static final Logger log = LoggerFactory.getLogger(OrderEventListener.class);

    private final EnvelopeCodec codec;

    public OrderEventListener(EnvelopeCodec codec) {
        this.codec = codec;
    }

    @KafkaListener(topics = Topics.ORDER_EVENTS)
    public void onEvent(ConsumerRecord<String, String> record) {
        MessageEnvelope envelope = codec.fromJson(record.value());
        switch (envelope.type()) {
            case MessageTypes.ORDER_CONFIRMED -> {
                OrderConfirmed event = codec.payload(envelope, OrderConfirmed.class);
                log.info("NOTIFICATION: order {} confirmed - {} x product {}, total {}",
                        envelope.orderId(), event.quantity(), event.productId(), event.total());
            }
            case MessageTypes.ORDER_CANCELLED -> {
                OrderCancelled event = codec.payload(envelope, OrderCancelled.class);
                log.info("NOTIFICATION: order {} cancelled ({})", envelope.orderId(), event.reason());
            }
            default -> log.warn("Ignoring unknown event type '{}' (messageId={})", envelope.type(), envelope.messageId());
        }
    }
}
```

````markdown
## 13. The saga (orchestration) and compensation

### What it is

A **saga** is one business action spread over several services, as a chain of
local transactions - each service commits its own part and sends a message. If a
later step fails, earlier steps are undone by **compensation**: a new command
that reverses the effect (put the stock back), not a database rollback.

### Why it exists

Each service has its own database (section 12), so there is no single
transaction across them. Two-phase commit (XA) would lock all of them and is
rarely available with Kafka. A saga accepts that the system is briefly in
between ("eventually consistent") and fixes failures with compensation.

### How it works here

```
order-service (the conductor)              other services
-----------------------------              --------------
PENDING      --ReserveStock-------------->  inventory: reserve
             <--StockReserved / Failed----
STOCK_RESERVED --ChargePayment----------->  payment: total <= 1,000 ?
             <--PaymentSucceeded / Failed-
CONFIRMED    --OrderConfirmed------------>  notification (order-events)
CANCELLED    --ReleaseStock-------------->  inventory: put the stock back   (only after PaymentFailed)
             --OrderCancelled------------>  notification
```

- Code: `OrderSagaService` - one method per reply. Each moves the order one state
  and writes the next message to the outbox **in the same transaction**.
- A reply that does not fit the state (late or duplicate) is ignored and sends
  nothing - e.g. `PaymentFailed` for a `CONFIRMED` order.
- Compensation (`ReleaseStock`) is fire-and-forget, as in the spec: no
  `StockReleased` reply. The outbox and the retries make sure it arrives; the
  release is naturally idempotent (only a `RESERVED` reservation is released).
- **Orchestration vs choreography:** here one service (order) tells the others
  what to do and decides the next step - the flow is in one class, easy to follow
  and debug. In **choreography** there is no conductor: each service reacts to
  the others' events (inventory hears `OrderPlaced`, payment hears
  `StockReserved`...). Fewer central parts, but the flow is spread over every
  service and harder to see.

  sold-out mug.
- What I saw: (final state and time for each order, the Laptop stock before and

### Interview answer

> "A saga is a chain of local transactions, one per service, connected by
> messages. When a step fails, the earlier steps are undone by compensating
> commands - here, payment fails and the order service sends ReleaseStock. I used
> orchestration: the order service is the conductor, so the whole flow is in one
> place. Every step goes through an outbox and every consumer is idempotent."

### Common follow-up questions

- *"Compensation vs rollback?"* - A rollback undoes an uncommitted transaction
  in one database. Compensation is a new business action that reverses a step
  that is **already committed** in another service.
- *"What if the compensation fails?"* - It is retried (outbox + error handler)
  and lands in the DLT if it never works - then someone must look. That is why
  compensations must be idempotent and simple.
- *"When choreography?"* - Few steps, teams that own their services and want no
  central coordinator. When the flow grows, orchestration is easier to change.

## 14. The asynchronous API (202 + polling)

### What it is

`POST /orders` answers **202 Accepted** with `status: PENDING` at once; the client
polls `GET /orders/{id}` until the status is final.

### Why it exists

The saga takes several messages and services. Holding the HTTP request open for
all of it would tie up threads and fail when any service is slow. 202 says "I
accepted your request, the work is still running".

### How it works here

`OrderController` returns 202 right after the order and its `ReserveStock` are
committed (section 8). `e2e-check.ps1` polls every 100 ms.

### What I saw

(time from POST to the final state for each path, from the end-to-end check)

### Interview answer

> "For a long, multi-service action the API returns 202 with an id and the
> client polls a status endpoint - or gets a callback or push. The request is
> fast and does not depend on every service being up."

## 15. Fan-out and when idempotency is not needed

- **Fan-out**: `order-events` is read by notification-service in its **own
  consumer group**. Every group gets every message, so adding another reader (an
  analytics service, an e-mail service) needs no change in order-service.
- notification-service is **not idempotent** on purpose: a duplicate
  `OrderConfirmed` gives a duplicate log line - harmless. A duplicate charge is
  not harmless, so payment-service is idempotent twice over (processed-message
  table + one payment per order). Choose per consumer.

## 16. Shared message contracts - the trade-off

All services use the `messaging-contracts` module (topic names, message types,
payload records). Simple for one repo and one developer. In real systems a shared
module couples teams: a change forces everyone to rebuild and release together.
Teams often keep their own copy of the message classes, or use a **schema
registry** (Avro / JSON Schema / Protobuf) that checks every change stays
compatible.
````
